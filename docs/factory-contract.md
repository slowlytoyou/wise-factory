# Factory integration contract · game 2.1 / save v3

Implementation contract shared by contributors. Runtime has no npm dependencies.

## Shared simulation

Canonical portable pure-JS engine: `supabase/functions/_shared/factory.mjs`.
Node entry `src/factory.mjs` re-exports it. No Node/Deno globals in engine.

Exports: `WORLD_WIDTH=41`, `WORLD_HEIGHT=29`, `MAX_RADAR_LEVEL=5`, `ITEMS`, `BUILDINGS`, `RECIPES`, `DIRECTIONS`, `createFactory(now=Date.now(), {demo=false}={})`, `advanceFactory(game,seconds)`, `applyAction(game,action)`, `serializeFactory(game,now)`, `hydrateFactory(raw,now,{offline=true}={})`, `tileAt(game,x,y)`, `buildingAt(game,x,y)`, `upgradeCost(building)`, `factoryStats(game)`.

Game shape: `{version:3, contentVersion:2, coins, lifetimeRevenue, soldCount, elapsed, stepRemainder, savedAt, player:{x,y}, merchant:{x:20,y:14}, buildings:[], stats:{sold:{},crafted:{}}, progression:{schema:1,unlocks:{smelter,assembler},radarLevel,transmitters,prestigeCount,cores,runRevenue}}`.
Buildings: `{id,x,y,type:'miner'|'belt'|'smelter'|'assembler'|'transmitter',dir:0..3,level:1..5,recipe:string,progress:number,buffer:{itemId:count},item:null|itemId,...}`. Transmitters stay level1 with no buffer/item/output; build consumes one inventory unit, recovery returns it, upgrades and rotation are unavailable.
Direction order 0=up,1=right,2=down,3=left. tileAt returns string `ground|iron|copper|coal|stone|wood|quartz|gold|merchant` using fixed terrain; copper is ground until radarLevel1, coal until2, wood until3, quartz until4, gold until5. New deposits occupy unused ground and preserve existing resource coordinates. Merchant occupies 3x3 centered (20,14). All tiles traversable by player except map edge; construction not on merchant. Buildings occupy one tile.
ITEMS has25entries:7rawmaterials and18products, ending in `research_paper` (논문), price6000. New raw IDs `wood,quartz,gold_ore`; new products `pulp,paper,glass,silicon,gold_plate,wire,chip,lens,sensor,research_device,research_data,research_paper`. ITEMS object, values `{name,glyph,color:[r,g,b],price}`.
BUILDINGS object by type `{name,cost,glyph,description}`. RECIPES object keyed recipe IDs with `{name,building:'smelter'|'assembler',inputs:{id:qty},output:'id',amount:1,seconds}`.
Actions independent from player proximity (player is construction cursor): `{type:'move',dx,dy}` or `{type:'build',x,y,building,dir,recipe?}` or `{type:'rotate'|'upgrade'|'remove',x,y}` or `{type:'recipe',x,y,recipe}` or `{type:'purchase',item}` or `{type:'prestige'}`. Return `{ok,message}`. Validate coords, costs, unlocks, type, recipe, levels, integer movements. Deterministic production, transport blocking, real item buffers and sale at merchant or adjacent transmitter. Never accept score/resource/progression setters as actions. Prestige mutates the existing game object in place.
advance returns `{earned,events}`. Simulation time must be independent from frame splitting. Offline max 8h, bounded CPU; hydrate returns `{game,offlineEarned,offlineSeconds}` and validates untrusted files. Starter includes a small working miner→belt→merchant route; demo includes multiple production chains. factoryStats returns `{rate,buildings,miners,belts,processors,inventory,...}` where rate is run revenue divided by elapsed simulation time, labeled as the current-run average.

Conveyor capacity is one actual `building.item` per tile. Incoming items may enter a belt's rear or sides, never its output edge (`target.dir === (source.dir + 2) % 4` rejects ingress). This also applies to producers delivering onto a belt. Facing belts jam rather than ping-pong cargo; perpendicular corners and side merges remain supported. Transfers into occupied belts wait, queues back up to the producer, and no goods are overwritten. Render occupied belt glyphs at a fixed direction-based slot, independent of `ui.time`; only simulation handoffs change the cargo's tile. Never use looping visual phases to move held cargo, including vertical belts and congested lines.

## Progression and save compatibility

`SHOP_ITEMS` ordered array: `smelter_blueprint`200, `assembler_blueprint`700 (requires smelter), `radar_copper`350, `radar_coal`900 (requires copper radar), `transmitter`250 repeatable; then `radar_wood`1800, `radar_quartz`3600, `radar_gold`7200, each requiring the previous radar. Originalfirst5shopindexes andfirst6recipeindexes remain unchanged. `shopOffers(game)` adds `{available,owned,reason}` including affordability. `buildingUnlocked(game,type)` gates production machines. All purchases are server checked. New games have no blueprints and radar0. Demo keeps existing smelter/assembler unlocks and radar2; additional radars are purchased normally.

`prestigeInfo(game)` returns `{available,gain,requiredRevenue,runRevenue,cores,multiplier,nextMultiplier}`. Threshold5000 run revenue, gain=floor(sqrt(runRevenue/5000)); permanent sale multiplier1+cores*.25. Prestige resets current factory, coins, unlocks, radar, transmitter inventory, elapsed and run statistics; it retains lifetimeRevenue, total soldCount, cores and prestigeCount. Starts a fresh starter line with300coins. All sale paths and cycle skips update runRevenue and lifetimeRevenue; average rate uses runRevenue/run elapsed.

Hydration reads v2/v3 and outputs v3. Saves include additive `contentVersion:2` to protect new catalog items during rolling cloud deployments. Only a legacy v2 record with no progression field gets both production blueprints and radar2 for compatibility. Files keep their historical `factory-v2.json` path. FactoryStore refuses unsupported progression schemas, save versions, and content versions without overwriting their bytes; cloud client/server reject unsupported stored formats before adopting or committing them. The monthly migration adds `factory_monthly_scores` and `factory_commit_monthly`, preserving save/content downgrade guards and committing factory state, monthly deltas, and receipts atomically. The old `factory_commit` returns update_required to stop older workers from omitting monthly accounting.

## Cloud interface

`src/cloud.mjs`: `readCloudConfig()` (environment and project config JSON), `CloudClient` constructor(config,{fetchImpl,sessionFile}={}); methods `login(provider='github',onUrl)`, `logout()`, `hasSession()`, `sync({revision,actions,requestId,nickname?})`, `leaderboard()`; async calls return payload or throw readable Error. Async `loadSession()` and `refreshSession()` manage the local session. PKCE loopback callback, access token refresh,0600 local session, no service-role credentials in client.
Server function `factory-sync`: `{revision,actions:[...],requestId,nickname?}` -> `{state,revision,nickname,offlineEarned?,results:[]}`. If revision omitted/null and no actions: load/create authoritative cloud factory. Never upload/import local state. Only server advances elapsed wall clock and applies actions; latest verified state is leaderboard source. Reject stale revisions with conflict and state, use atomic CAS/SQL transaction and requestId idempotency to prevent duplicate spend across retry. `factory-leaderboard` or op inside same endpoint -> `{entries:[{rank,nickname,score,goldPerSecond}],me:{rank,nickname,score,goldPerSecond}|null,month:"YYYY-MM",resetsAt:ISO,timezone:"Asia/Seoul"}`. Score is floored current-month server-verified revenue, goldPerSecond is current-month verified revenue/current-month simulatedSeconds (0 when no credited time). Months reset atKST00:00 onday1 without resetting factory/lifetime revenue/cores; offline simulation is capped to the last8h before sync and split at each month boundary. Client leaderboard displays monthlyscore/rate/reset notice, refreshes every60s and atresetsAt, clears expired cached ranks before fetch, and handles missing/invalid rates as0. RLS denies direct write of state/score; service-role server only.
CLI behavior: local game uses local saves; `--cloud` requires configured project+login and loads server state. Cloud gameplay predicts locally between accepted state syncs, queues actions in order and reconciles to server responses. During unavailable network freeze new cloud construction and offer local mode via a later restart; never silently upload local scores. Sync action promptly, idle at60s. Online pause pauses presentation only (server time keeps running); disclose.

Default `npm start` and explicit `npm run local` / `--local` are private play: no cloud module loading, config/session reads, or network calls. Local `L` shows personal factory records under the existing `ui.leaderboard` modal flag; only cloud mode loads global rankings. Login failure leaves local saves and existing cloud sessions intact. Explicit login first GETs `/auth/v1/settings` and requires `external[provider] === true` before creating the callback listener or opening the browser. Disabled providers produce a friendly error with `npm start` guidance. A successful login does not change the default mode or merge save slots.

`CloudGame` spaces requests by 600ms and exposes `retryDelayMs`, `retryAt` and `needsSync`. A cooldown returns `{ok:false,deferred:true,retryAt}` without dispatching; an acknowledged replay can return `{ok:true,deferred:true,retryAt}` while fresh catchup is still needed. `CloudError.retryAfterMs` carries a valid Retry-After seconds/date value. HTTP429 keeps the exact pending request and uses `rate_limited` until automatic retry (60s fallback); authentication failure uses `error`, network failure `offline`. The CLI timer retries online pending work and rate-limited requests after the deadline. Shutdown flushes in-flight and queued actions with short waits, but never claims success while work remains unconfirmed. `--cloud --save PATH` is rejected before config/session/file access; cloud cache cannot overwrite an explicitly supplied personal save.

N opens the nickname editor (`nicknameEditor`, `nicknameDraft`, `nicknameError`, `nicknameSaving`). Enter validates/saves, Escape cancels, Ctrl+U clears and Backspace deletes a grapheme; gameplay shortcuts are consumed as text while editing. The local `game.nickname` is an optional backward-compatible v3 field, defaults to 공장장, and survives prestige. The cloud public nickname remains separate server response/row metadata. `CloudGame.setNickname(value)` queues a validated normalized name and `pendingNickname` exposes the latest intention; only server confirmation changes the visible name. Pending payloads remain immutable across retry and later edits. Revision conflicts adopt the server name and discard queued renames explicitly. Name normalization matches the existing cloud API (NFKC, trim, collapse spaces, 2–20 Unicode letters/numbers/spaces/_/-). No server schema or API change is needed.

The T prestige modal always explains cores before and after prestige eligibility: each core adds25% of base sale price, holding cores applies the bonus automatically without spending them, merchant/transmitter sales both benefit, and4cores means2×. Confirmation remains E/Enter followed byY.
